# Target onboarding

Status: common tooling implemented and personal deployment verified. Organization and additional-target live onboarding remain unverified. Changing target identities requires no controller edits or image rebuild.

1. Run [host preflight](01-host-preflight.md). Establish trusted workflows, toolchains and resource limits. Current personal capacity consumes all four slots: redistribute before adding another target, or separately approve and verify a larger host budget.
2. Choose `repository` scope for a personal repository or `organization` scope for shared organization capacity. Confirm administrator authority and allowed repositories. Organization capacity is shared across allowed repositories. Verify organization plan/access settings during onboarding.
3. Create or select a GitHub App: repository Administration write for repository registration; organization Self-hosted runners write for organization registration. Disable incoming webhooks. Install under the intended owner and record actual App/installation IDs. Each owner needs its own installation; labels do not grant access. Follow [App setup](05-github-app-setup.md).
4. Save its key under ignored `.local/secrets/` and restrict access with `./scripts/github/Protect-RunnerAppKey.ps1 -Path .local/secrets/<your-key>.pem`. Never mount it in jobs or record its contents.
5. For a fresh installation, copy `config/targets.example.json` to `.local/targets.json` and remove unwanted targets. For an existing installation, add an entry to its `targets` array; do not overwrite working configuration with the example. Set unique `id`, `scope`, `owner`, `repository` (null for organization), actual `appId`/`installationId`, protected `privateKeyFile`, distinctive `labels` and `maxRunners`. Example null IDs are incomplete. `Initialize-PersonalTarget.ps1` is a convenience for the initial example, not a generic add-target wizard.
6. Run `./scripts/config/Test-RunnerConfiguration.ps1 -Path .local/targets.json`, then `./scripts/github/Test-RunnerGitHubAccess.ps1 -ConfigPath .local/targets.json`. These validate structure, aggregate capacity, installation owner/permissions and runner API access. They do not prove successful registration/jobs. `-AllowIncomplete` is only for inspecting examples, never deployment.
7. Apply through `./scripts/host/Restart-RunnerService.ps1`. It drains the old controller, preserves active jobs and loads the new targets. Inspect `./scripts/host/Test-RunnerService.ps1` and `./scripts/controller/Test-RunnerPool.ps1`. Follow [operations](08-personal-operations.md) for service installation and maintenance.
8. Update intended workflows to select their target labels, for example `runs-on: [self-hosted, linux, <your-target-label>]`. Run trusted smoke jobs; verify a second job gets a fresh runner/workspace and prior resources are destroyed. Record access settings and sanitized evidence. Image reuse does not automatically migrate workflows or grant cross-owner access.

To roll back an added target, restore the previous non-secret configuration and gracefully restart. Retain its key until its jobs have drained.

The validator rejects duplicate IDs/identities and excessive aggregate capacity; the App client rejects installation owner/scope/permission mismatches. These checks are tested. A second real target has not yet been onboarded. GitHub authorization, key provisioning and workflow label changes remain manual steps; there is no universal one-command onboarding wizard.
